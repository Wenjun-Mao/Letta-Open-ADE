## Root cause at the binding contract

The only difference in the comparable base packets is `reviewer_packet.targets`: `person.current_location=北京` and `relationship.person=小王` are the same logical inactive targets, but their list order reverses. The reviewer assigns `F1` and `F2` in that input order, so the model-facing handle-to-fact mapping differs across arms. The facts were seeded in a single transaction in each cell, with equal `created_at` values; a direct database query showed their random UUIDs sort in opposite orders. `MemoryRepository.list_facts_with_entities()` orders by `(created_at, id)`, and `build_natural_binding_map()` enumerates that returned order into `F#` handles. The output mismatch therefore originates in unstable logical target ordering at the binding input, not in H2 ranking, history admission, provider captures, or a fixture difference.

A durable follow-up is to define a canonical reviewer target order by stable semantic identity before assigning handles, and test equivalent fact sets with reversed database ID order. The ordering contract must account for otherwise identical facts and related entity handles; it should be reviewed as a model-facing contract change before any new comparison. No normalization was applied to this campaign's recorded packets, and the failed equality gate was not waived. A new source freeze and authorization would be needed for further live turns.
