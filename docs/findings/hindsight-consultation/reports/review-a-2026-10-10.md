## Recommendation

**Freeze new native-memory feature work, but do not make a behavior-preserving native-memory refactor the prerequisite for learning whether Hindsight works.**

The next iteration should be **a disposable, evaluation-only Hindsight-to-Character slice**: attributed synthetic exchanges → real pinned Hindsight retain/recall → a small ADE request composer → the existing `ConversationExecutor`. Keep it outside normal ADE run finalization initially.

That is deliberately narrower than a production integration. It tests the largest unknown—whether Hindsight can supply useful, correctly scoped conversational memory—without first restructuring the incumbent transaction, reviewer, embedding pipeline, and inspection API.

**For that experiment, I would try one bank per workspace/user, caller-assigned character scopes, and Hindsight-native extraction labels for shared profile facts.** Treat this as the first candidate to test, not a settled production layout. The pinned version documents extraction-time labels that can become memory tags, a capability that materially strengthens the one-bank option beyond the assessment’s discussion of caller-supplied tags. Its `LabelGroup` and `build_labels_model` source support the configuration mechanism; end-to-end classification quality remains untested. [Hindsight bank configuration](https://github.com/vectorize-io/hindsight/blob/eb6df499d35300e5b2f3f029b2e6adda04ed90f8/skills/hindsight-docs/references/developer/api/memory-banks.md), [`entity_labels.py`](https://github.com/vectorize-io/hindsight/blob/eb6df499d35300e5b2f3f029b2e6adda04ed90f8/hindsight-api-slim/hindsight_api/engine/retain/entity_labels.py).  

My other principal changes to the proposal are:

- Prefer **immutable exchange documents**, not a continually replaced conversation document.
- Preserve **eventual delivery of every accepted input**, but defer the production outbox/worker until the product experiment succeeds.
- Keep **committed assistant-message ingestion**. Without it, your allowed fictional history has no dependable route into memory.
- Amend native transaction and inspection contracts explicitly; do not reproduce them through dummy reviewer results or invented Hindsight “fact versions.”

These are architectural recommendations. Nothing inspected establishes Hindsight’s conversational quality or operational suitability for ADE.

## 1. Responsibility and data-flow sketch

```text
ADE owns:
  user/workspace identity, character root, persona version
  accepted user inputs, committed replies, conversation/run state
                         │
                         │ attributed, immutable source units
                         ▼
Hindsight owns:
  extraction → entities/facts → indexing/retrieval
  character-scoped consolidation → memory curation
                         │
                         │ scoped recall results
                         ▼
ADE Character request composer:
  bound persona + ADE requirements + current/local dialogue
  + relevant memories + permitted tools/results
                         │
                         ▼
existing ConversationExecutor → Model Router → Character reply

Later runtime integration:
  ADE commits reply/run outcome independently of memory processing.
  A small delivery record connects committed sources to Hindsight.
```

### What Hindsight should own

Let Hindsight own semantic extraction, entity handling, memory representation, embeddings, retrieval/reranking, temporal interpretation, consolidation, and the state of its curated memories. Its documented recall path already combines semantic, keyword, graph, and temporal retrieval. Building another ADE retrieval engine around it would defeat the replacement. [Recall contract](https://github.com/vectorize-io/hindsight/blob/eb6df499d35300e5b2f3f029b2e6adda04ed90f8/skills/hindsight-docs/references/developer/api/recall.md). 

ADE should supply the meaning of its identities and product boundaries, not independently re-extract or adjudicate the same memories.

| ADE responsibility | Minimum implementation | What not to add |
|---|---|---|
| Bind ownership | Deterministic bank and character-scope selection from existing IDs | Model-selected bank IDs; similarity-based character identity |
| Supply sources | Attributed text, source IDs, timestamps, and limited conversational context | Native fact conversion; a second semantic reviewer |
| Deliver sources | Eventually, a small delivery receipt/retry mechanism | A new event platform or remote-transaction abstraction |
| Compose Character requests | One concrete composer and a Hindsight recall tool binding | A generic memory-provider framework |
| Expose removal | Hindsight-native targets and truthful outcomes | Fabricated native revisions, generations, or atomicity |

**Keep local dialogue management.** ADE’s compaction code manages a bounded recent-message window and durable conversation summaries; that is a different responsibility from long-term memory consolidation. Its current `compact_turn` wrapper also contains native lifecycle-policy dependencies, so reuse the underlying conversation-window functionality rather than assuming the whole wrapper is backend-neutral.  

## 2. Sequencing: learn before preserving the wrong boundary

The assessment correctly identifies coupling. In the inspected ADE source:

`select_turn_context` sizes Character context together with reviewer capacity. `TurnExecution.execute` creates reviewer and embedding collaborators, then returns an `AttemptResult` that requires their outputs. `RunFinalizer.commit_success` checks the accepted memory generation and commits native memory changes before the assistant message within the same transaction. These are real incumbent contracts, not a replaceable search callback.     

However, **that does not establish that isolating those contracts is the best next investment.**

| Route | Learning value now | Rework and complexity | Recommendation |
|---|---|---|---|
| Isolate incumbent first | Good information about native refactoring; little about Hindsight quality | Risks polishing interfaces whose transaction and record assumptions will be discarded | Freeze development, but defer broad isolation |
| Test Hindsight independently | Fastest way to expose extraction, attribution, scope, and provider problems | Small throwaway harness; does not test Character composition | Use as the opening smoke test, not a separate preparatory project |
| Thin memory-to-Character slice | Tests memory usefulness and actual downstream behavior together | A concrete client, source formatter, composer, and evaluation entrypoint | **Best next iteration** |

The useful existing seam is [`ConversationExecutor.execute`](https://github.com/Wenjun-Mao/Letta-Open-ADE/blob/c46ac380a81a89775c25c4c0edf49825a222d91b/services/ade-api/src/ade_api/features/agent_runtime/executor.py): it already accepts prepared messages and a tool dictionary. It does not require native memory rows. That supports an evaluation path without first routing Hindsight through `TurnExecution` and `RunFinalizer`. 

**My inference:** refactoring those two orchestration classes before a real memory experiment offers less learning per change than a thin evaluation binding.

The simpler alternative to a behavior-preserving isolation project is to preserve the commit and tests, leave native execution untouched, and reuse only already-useful components. Exact native request preservation becomes relevant when you change native execution—not as a prerequisite for a separate experiment.

## 3. Ownership: test native classification before adding a shared-profile pipeline

### First candidate

Use:

```text
bank = workspace_id + memory_subject_id

caller-assigned source scope:
  character:<agent_definition_root_id>

Hindsight-extracted sharing label:
  kind:profile
```

For Character C, recall facts matching:

```text
character:C OR kind:profile
```

Use a nonempty strict filter, selected by ADE—not supplied by Character. Missing profile classification should leave a memory character-local, not shared.

Conversation ID and persona-version ID remain provenance. They do not change continuity scope. Archive status should not change the bank or character tag.

The native mechanism is a small `entity_labels` configuration with `tag: true`, plus a retain mission describing attribution and what qualifies as an independently useful user-profile fact. This is **configuration of Hindsight’s extractor**, not another ADE extraction pass. The pinned docs distinguish that mission—which supplements built-in extraction—from custom instructions that replace the extraction rules; start with the former. 

### Keep consolidation character-local initially

For inputs from Character C, test an explicit observation scope equivalent to:

```text
[["character:C"]]
```

This allows consolidation within that relationship while sharing selected **raw profile facts** across characters. Do not introduce shared observations yet.

That is an important simplification: you need not solve cross-character profile consolidation to test cross-character profile availability. The pinned retain contract documents explicit observation scopes and says resulting observations carry the scope’s tags. This is a documented capability to verify, not independently demonstrated enforcement. 

### Keep source documents private to their character scope

Do not label a whole conversation document `kind:profile` merely because one extracted fact is shareable.

The pinned recall contract explicitly distinguishes memory tags from document tags: a fact can match an extraction-derived label while its source chunk is withheld because the document does not match that scope. That directly addresses the risk of sharing an innocent profile fact together with another character’s private dialogue. [Recall source-chunk rules](https://github.com/vectorize-io/hindsight/blob/eb6df499d35300e5b2f3f029b2e6adda04ed90f8/skills/hindsight-docs/references/developer/api/recall.md). 

For the first Character path, omit raw chunks and diagnostic source bundles by default anyway. Return useful memory text and attribution, not whole transcripts.

### What this does—and does not—solve

There are two different questions:

**Which user owns this data?** ADE can answer mechanically by selecting the user’s bank.

**Is this extracted sentence shareable profile information or character-private history?** That is semantic interpretation. Hindsight can perform it, but its correctness must be tested.

A native label is not proof of correct classification. For example:

> “The user likes jasmine tea, which Xiaotang introduced during their private anniversary conversation.”

Sharing that entire sentence would leak relationship context even if `kind:profile` is assigned correctly in a narrow sense. The extractor must separate the preference from the private exchange.

This is why I recommend the layout **as an experiment**, not as an established authorization solution.

### Why separate banks are not automatically simpler

Separate relationship and profile banks give stronger physical separation, but they do not decide what belongs in the profile bank. Sending the same dialogue to a “profile-focused” bank still relies on semantic extraction—and can duplicate processing, corrections, and removal work.

Therefore, I would not commit to two extraction routes before testing native labels.

If that test fails, retain separate banks as the fallback candidate. Do not immediately compensate with an ADE classifier, semantic post-filter, and reconciliation engine.

For an ADE-only backend, a custom tenancy extension is also not an immediate prerequisite. ADE can bind banks and scopes behind its product API. Hindsight’s default tenant implementation is unauthenticated; its built-in API-key extension authenticates access to one configured schema rather than authorizing individual ADE users. Network access must reflect that distinction. [`DefaultTenantExtension` / `ApiKeyTenantExtension`](https://github.com/vectorize-io/hindsight/blob/eb6df499d35300e5b2f3f029b2e6adda04ed90f8/hindsight-api-slim/hindsight_api/extensions/builtin/tenant.py). 

## 4. Ingestion, delivery, freshness, and removal

### Prefer immutable exchanges over a growing conversation document

My first source unit would be **one terminal exchange**:

- The accepted user input.
- The committed assistant reply, when one exists.
- A bounded amount of preceding dialogue needed to resolve references.
- Explicit speakers, source IDs, ordering, timestamps, character root, and persona version.

A failed or cancelled run still produces an eligible user-only source unit. Uncommitted assistant candidates never become sources.

This challenges the assessment’s timing: **eligibility begins at acceptance, but ingestion need not begin immediately at acceptance.** Waiting until the exchange reaches a terminal state permits one immutable attributed unit instead of separate continually revised documents. Character already has the current input for its immediate response.

The incumbent already persists the accepted user message independently of later success, so that source exists even if generation fails. [`RunService.accept_turn`](https://github.com/Wenjun-Mao/Letta-Open-ADE/blob/c46ac380a81a89775c25c4c0edf49825a222d91b/services/ade-api/src/ade_api/features/agent_runtime/run_service.py). 

Should delivery before terminalization prove necessary, use immutable per-message units instead. That timing requirement would not justify mutable whole-conversation replacement by itself.

### Why not start with replacement or append?

The pinned retain documentation recommends retaining updated conversations under the same document ID and describes both replacement and append/delta processing. Separately, its curation documentation explicitly states that **reprocessing a document resets curation of its extracted facts**. The exact incremental paths still need testing, but the interaction is sufficient reason not to make a mutable conversation document the default architecture.  

Immutable exchange units reduce three problems: old revisions overwriting newer ones, routine re-extraction of old content, and maintenance undoing operator curation.

They introduce a different uncertainty: whether bounded context preserves attribution and referential meaning. That is a cheap comparison to run, not a reason to design an episode store.

**Important limitation:** immutability does not eliminate semantic duplication. Repeating an old fact in the context of a new exchange could extract it again. Include that exact case in the removal experiment; do not claim that document IDs alone solve it.

### Retain committed assistant text—but not as unquestionable truth

I agree with assistant ingestion. Your product permits Character to establish solo fictional history, so user-only ingestion leaves a fundamental hole.

However, the extraction mission must distinguish:

> “Character told a solo story”  
> “Character proposed a hypothetical”  
> “Character asserted something about the user”  
> “The user actually established that fact”

Ingestion records what was said; it does not automatically validate the claim. Test this through Hindsight’s extraction and Character’s resulting behavior, not through a second ADE judge.

### Durable delivery is necessary later; a new outbox is not necessarily necessary

For the evaluation slice, synchronous retain calls are sufficient. They remove queue lag as a confound when testing memory quality.

For runtime adoption, I would first consider **the existing durable source records plus a small delivery-receipt table**, rather than automatically creating a new source-event system. The receipt needs to connect an immutable source unit and payload to its bank, operation, and processing status. ADE can discover undelivered sources from its persisted messages/runs.

This is a design proposal, not a claim that the existing repository already implements a suitable scanner.

Hindsight’s request model supports both synchronous/asynchronous processing and a caller-provided `operation_id`. Its queue can own extraction execution after receipt; it cannot, by itself, close the gap before ADE successfully delivers committed content. 

The eventual requirement is durable delivery—not a particular queue architecture, broker, or worker service.

### Make freshness weaker and clearer than native snapshot semantics

Do not reproduce `accepted_memory_generation` for Hindsight.

The native snapshot and retrieval code rejects generation changes after acceptance, and finalization checks that generation again. That is an incumbent consistency choice, not a demonstrated requirement for natural Character continuity.  

Start with:

**Current dialogue is immediate; long-term recall is eventually updated.**

For the semantic experiment, wait for retain completion before testing a new chat. For a later interactive binding, distinguish ingestion pending, retrieval unavailable, and no relevant result. Do not fail an otherwise valid reply simply because another conversation changed memory.

Also, do not equate extraction completion with consolidation completion. The pinned recall docs explicitly describe observations as potentially lagging raw retained facts. 

### Removal: native curation, not an ADE suppression engine

Hindsight documents invalidation of raw `world` and `experience` memories, removal from active recall, and recomputation of derived observations. Observations are not directly curated through the same mechanism.  

Use that native model. ADE should prevent routine redelivery/reprocessing from undoing it.

Consequently, **Hindsight should be authoritative for its derived memory and curation state—not treated as a disposable index automatically rebuilt from unchanged ADE transcripts.**

Keep the promise narrow: removal of selected memories is not permanent semantic suppression of a topic. Historical messages remain, and genuinely new statements can be learned. Rebuild/backfill behavior needs an explicit later decision; a universal tombstone matcher does not belong in this next iteration.

## 5. Keep request composition concrete

A small `compose_character_request(...)` function or module is sufficient. It should combine the bound persona and ADE requirements with current/local dialogue, render relevant memories with useful attribution and dates, and attach the permitted tools.

It should **not** translate Hindsight memories into `normalized_key`, native fact `version`, revision lineage, or `memory_subject_role=current_user`.

That last point is a concrete integration trap. ADE’s existing `SEARCH_MEMORY_TOOL` says returned facts never describe the assistant persona, and `_search_memory_tool` wraps everything as current-user facts. Those semantics are wrong for Hindsight-backed character history. Supply a Hindsight-specific `CuratedTool` through the executor’s existing tool mechanism rather than reusing that wrapper unchanged.  

Keep one serialization path for the initial call and tool continuations. `ConversationExecutor.execute` already serializes each step, can check `input_token_limit`, and carries the returned assistant message into continuation. Pass the limit explicitly in the new binding. Hindsight’s `max_tokens` only budgets fact text and can return an oversized first fact; it is not a whole-request capacity guarantee.  

An initial automatic recall plus optional Character-directed recall is a reasonable starting policy. No required `reflect` phase, query-planner model, evidence-admission packet, or extra personality-judgment stage is needed.

### Explicit contract amendments

A short experimental decision record is sufficient now; a comprehensive adoption ADR can wait.

| Contract area | Amendment for the Hindsight binding |
|---|---|
| PC-05 | Hindsight performs memory interpretation; ADE no longer requires native reviewer decisions and operation embeddings for each reply |
| PC-08 | ADE remains authoritative for conversations/runs and the product API; Hindsight owns separate memory persistence and curation |
| PC-09 | Permit the concrete Hindsight client/service boundary and, later, necessary delivery tracking—not a generic backend framework |
| PC-07 technical API | Expose Hindsight targets and truthful per-operation outcomes; do not promise native generations, revisions, or multi-target atomicity |

The existing removal API specifically requires expected fact versions and a subject memory generation, and its response reports native revisions. Those are contracts to change, not fields to fabricate.  

PC-02/03/04/10/11 and the excluded no-save/phrase-policy features do not need reopening.

## 6. One bounded next iteration

### Deliverable: an evaluation-only Hindsight memory-to-Character binding

Limit it to one pinned Hindsight configuration, one concrete client/formatter, one composer, the existing executor, and synthetic transcripts. No normal run finalizer changes, production worker, existing-chat export, migration, or Studio redesign.

Start with independent retain/recall smoke calls, then use the same memories in actual Character requests. Fake transport tests are useful for request shape, but cannot substitute for the semantic portion.

Use four compact scenario bundles:

| Scenario | What it resolves |
|---|---|
| **Ownership and sharing:** two users, two characters, one profile preference, distinct relationship/solo stories; repeat across persona version and archive metadata, before and after consolidation | Whether native labels and scopes make the one-bank design viable; whether sharing drags private context along |
| **Attribution and continuity:** a referential “yes, that one,” a committed solo story, a joke/hypothetical, an unsupported assistant claim about the user, and a later question about an unstated detail | Whether source packaging and extraction preserve meaning without a second reviewer; whether Character invents missing recollections |
| **Curation and source replay:** invalidate one memory, deliver a new exchange, retry an old source, and repeat old text as context | Whether immutable units plus delivery discipline suffice, or whether source packaging has a real removal problem |
| **Actual request path:** ordinary recall, unavailable recall, oversized memory/tool content, and one tool continuation | Whether the composer/executor boundary works and preserves natural responses without native record emulation |

Use Chinese dialogue where appropriate for the intended character. For a few key questions, compare Hindsight memory, no memory, and a manually supplied adequate-memory control through the **same Character request path**. This helps distinguish extraction/retrieval failure from answering failure without building another evaluator subsystem.

The learning outcomes should be specific:

**Can the proposed scopes preserve the product boundaries? Can Hindsight retain enough attributed story detail? Does immutable exchange ingestion work? Does the intended model configuration actually run at acceptable latency? Does Character use the memories naturally?**

A negative result is useful. It should select the next change—source packaging, native configuration, bank layout, or reconsideration—not trigger an automatic expansion into an ADE memory engine.

### Actual prerequisites, and simpler alternatives

| Prerequisite | Immediate risk addressed | Simpler sufficient form |
|---|---|---|
| Record the experimental contract exceptions | Accidentally claiming native transactional/removal guarantees | A short binding-specific note |
| Bind identities outside the model | Cross-user or cross-character scope selection errors | One deterministic mapping function; no tenancy framework |
| Provide an isolated synthetic environment and viable model configuration | Touching real data or spending the iteration on an unusable provider path | One candidate setup and smoke test; no deployment matrix or backup audit |
| Keep actual requests/results inspectable | Misdiagnosing missing retrieval as Character failure | Capture fixture inputs, recall output, final request, and reply; no evidence-packet architecture |

Everything else—durable delivery implementation, broad native isolation, backfill, shared-profile consolidation, recovery tooling, and full UI integration—can wait for these results.
